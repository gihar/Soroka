## Вердикт по специфичности дизайна

**Расщепление личности.** Вход и выход продукта — авторские и по бренду: `welcome_message()` открывается делом без украшений («Превращаю записи встреч в протоколы», message_builder.py:37-44), итоговое резюме дисциплинированно (146-173). Середина — обработка, очередь, ошибки, меню — генерический «живенький» бот-филлер, который бренд прямо называет анти-референсом: 🚀, 🎭, «⚡ Скоро начнем обработку!». Команда умеет попадать в «нейтральный, надёжный, лаконичный» — шумная середина это провал консистентности, не навыка.

**Детерминированный скан.** `detect.mjs` вернул exit 0 и `[]` — но это «нет сканируемых файлов», а не «чисто»: детектор веб-разметки не читает `.py` (гейт расширений в detect-text.mjs:31). Вместо него — механический скан строк (metrics.py, AST, 27 файлов, 1927 строковых юнитов, логовые исключены):

- **675 эмодзи** в пользовательских строках, **71 уникальный глиф**; ❌ (214) + ✅ (65) = **41% всех эмодзи**.
- Топ по плотности: сообщения с 5-8 эмодзи (admin_handlers.py:611, message_builder.py:257 — 1145 символов и 6 эмодзи).
- **66 из 81** уникальных подписей кнопок начинаются с эмодзи.
- parse_mode: **Markdown 115 / HTML 4 / None 4** — HTML-острова в result_sender.py и card_sender.py; message_builder.py мешает `**` и `<b>` в одном файле; 4 вызова без parse_mode → пользователь видит литеральные звёздочки (`**Настройки бота**`, quick_actions.py:249-253).
- Английских артефактов в прозе — **0** (3 находки — false positives, placeholder `action_items`).
- Восклицаний всего 13 — «SMM-тон» локален (очередь/прогресс), не тотален.

**Совпадение A и B:** перегруз эмодзи подтверждён числом; коллизия словаря (📊 28 употреблений, 🔄 24, 📋 18 — каждый в 3-5 значениях). **B поймал, что A пропустил:** дубли длинных админ-сообщений (849×2, 911×2 символов), два глифа «Отмены». **Визуальные оверлеи:** n/a — Telegram-бот, веб-страницы нет.

## Общее впечатление

Каркас UX здоровый: статус виден, выходы есть, help хороший, быстрый путь для повторных пользователей продуман. Но самые долгие минуты пользователя — ожидание обработки — обслуживает самый шумный экран продукта, а словарь эмодзи, задуманный как навигация, выродился в шум: глиф, означающий пять вещей, не означает ничего. Самая большая возможность: один фиксированный лексикон ≤10 глифов и тихий экран прогресса.

## Что работает

1. **Welcome и /help** — продукт с первой строки, ноль украшений (message_builder.py:37-44, 47-63). Эталон для остальных экранов.
2. **Дисциплина итогового резюме** — только релевантное читателю, техдетали в логи (message_builder.py:146-173).
3. **Предупреждения о последствиях простым языком** — «Неназванные спикеры попадут в протокол как „Участник N"» (speaker_mapping_ui.py:26, 325).

## Приоритетные проблемы

### [P1] Эмодзи: украшение + коллизия словаря (ядро жалобы, подтверждено)
- **Что:** декоративные 🎭 (card_content.py:57), 🚀 (quick_actions.py:65,320), ⚡/💡 в очереди (queue_tracker.py:53-82); один глиф — много значений: 📊 = статистика/размер файла/проекты/очередь, 🔄 = обработка/сброс/повтор, 📋 = 5 значений, ✅ = успех/радио/подтверждение. 675 эмодзи, 71 глиф.
- **Почему важно:** маркер с пятью значениями не маркирует ничего; нарушает бренд-правило «эмодзи только как навигационные метки».
- **Фикс:** фиксированный лексикон ≤10 глифов (один глиф = одно значение), удалить 🎭🚀⚡💡 и линию-разделитель, максимум один ведущий эмодзи на строку, один глиф «Отмены».
- **Команда:** /impeccable quieter

### [P1] Экран прогресса — самый шумный в продукте
- **Что:** `✅ 📁 Подготовка · 12с` / `🔄 🎯 Транскрипция /` — два эмодзи + ASCII-спиннер на строку (progress_tracker.py:309-318); плюс двойной штамп успеха: «✅ Обработка завершена!» → «✅ Протокол готов» (progress_tracker.py:285 → result_sender.py:69).
- **Почему важно:** экран, на который смотрят дольше всего, должен быть самым спокойным; три глифовые системы плющат иерархию.
- **Фикс:** один статусный глиф на строку, убрать пер-этапные эмодзи и спиннер; подавить кадр «завершена», когда следом идёт резюме.
- **Команда:** /impeccable quieter

### [P2] Ошибки: канцелярит-шаблон, сырой машинный вывод, тупики
- **Что:** формуляр «**Тип:** … **Детали:** …» (message_builder.py:83-101); `_escape_markdown` доставляет пользователю `Timeout after 30s\.` (progress_tracker.py:405,424-430); ~20 хендлеров отвечают голым «❌ Произошла ошибка»; булет про автосжатие противоречит ошибке «файл слишком большой» (message_builder.py:222-231).
- **Почему важно:** бьёт сразу два анти-референса — канцелярит и сырой машинный вывод; ошибка без следующего шага = обращение в поддержку.
- **Фикс:** тиражировать голос result_sender.py:275-278 («Протокол не получился: … Отправьте запись ещё раз») — одно простое предложение + один следующий шаг; убрать противоречащий булет.
- **Команда:** /impeccable clarify

### [P2] Фрагментация разметки: Markdown/HTML/None
- **Что:** 93% Markdown, но HTML-острова (result_sender, card_sender), `**`+`<b>` в одном message_builder.py, и 4 вызова без parse_mode — литеральные `**звёздочки**` у пользователя (quick_actions.py:249-253).
- **Почему важно:** это не стиль, а класс багов: часть сообщений уже рендерится сломанной.
- **Фикс:** один канонический режим (ADR по прецеденту card_sender HTML), линт на строки с `**` без parse_mode.
- **Команда:** /impeccable harden

### [P2] Машинные термины и терминологический дрейф
- **Что:** `SPEAKER_1 → Не определен ❓` (card_content.py:59-63), «LLM провайдер» (message_handlers.py:180), «AI модели»/«Модель ИИ», `MB`/`МБ`, «В файл pdf»/«В файл Word», два слогана фидбека.
- **Фикс:** таблица терминологии; спикеры как «Голос 1»; «модель» вместо «LLM провайдер».
- **Команда:** /impeccable clarify
